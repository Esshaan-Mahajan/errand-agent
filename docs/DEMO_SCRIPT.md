# Demo recording script (3 to 5 minutes)

The assignment asks for a screen recording, posted on Loom or as an unlisted YouTube video. Only you can record and upload this, so here is a script for it. It shows one full booking and two failures handled live, with the agent's chat and its trace side by side.

## Before recording

Use the real model if you can. It's what the assignment means by "real LLM", and the UI labels which model is running.

```bash
export OPENAI_API_KEY=your-key
python -m errand_agent.web --live --data data/demo --traces data/demo-traces
```

No key? This runs the offline stand-in. Everything below still works, but say on camera that it's a rules-based stand-in, not an LLM.

```bash
python -m errand_agent.web --data data/demo --traces data/demo-traces
```

Open http://127.0.0.1:8765 and make the browser window wide. Delete `data/demo` first if you've run it before.

## Script

**0:00 Intro (20 s).** "Chat on the left, live trace on the right, both from the running agent. Everything is local: mock providers, no real payments."

**0:20 Full booking with a timeout-after-success (2 min).** Scenario: `timeout-after-success`.

1. Send: `Find a plumber for my kitchen tap this week, mornings only, under 1,500.`
   Point out that it asks only for the area, since everything else was given.
2. Send: `Indiranagar`
   In the trace, point at `search_providers`, `get_provider`, `hold_slot`, then `proposal`. The prompt shows the exact provider, slot and price, and that text comes from code, not the model.
3. Send: `yes`
   This is the key moment. In the trace:
   - `reply_classified`: code read the yes, and this run makes no model call.
   - `approval_recorded`: durable before any side effect.
   - `tool book ... ERROR timeout`: amber. It may or may not have committed.
   - `tool get_booking_status`: the source of truth says booked.
   - `VERIFIED`, and only then the chat says "Booked and verified".
4. Send: `yes` again.
   "A repeated confirmation doesn't book twice." The bookings panel still shows one.

**2:20 Proactive follow-up (45 s).** Click **Provider cancels**.

Within two seconds the chat shows a message nobody asked for. In the trace: `cancellation detected`, then `followup_decision` (whether and how to notify), then a new proposal. Point out that nothing was rebooked: it needs a fresh yes. Send `no`.

**3:05 Restart (20 s).** Optional, if time allows. Click **Restart process** and send `what do you remember about me?` to show state survived.

**3:25 Prompt injection (1 min).** Switch the scenario to `prompt-injection`.

Offline, this scenario uses a stand-in model that *obeys* the injected review, which is the worst case. With `--live` the real model should simply ignore it, so show that instead.

1. Send: `Find a plumber in Indiranagar this week, mornings only, under 1,500.`
2. In the trace, point at `untrusted content`, then the red `GUARD BLOCKED` lines: the model tried to call `book`, hold the attacker's provider, store a poisoned memory and fake a proposal. All four were refused. The bookings panel is still empty.

**4:25 Close (20 s).** Show `evals/results/EVAL_TABLE.md`: "generated by the test run, with invariants checked after every scenario."
